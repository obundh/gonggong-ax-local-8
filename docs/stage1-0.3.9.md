## 보관 위치와 제한

- 후보 DB와 페이지 정렬 자료는 `recovery-workspace/candidate-jobs/<작업 ID>/`에 저장한다. SQLite 임시 연산은 OS 임시 폴더로 쓰지 않도록 설정한다. 원시 볼륨 검색은 작업 공간과 원본의 물리 디스크가 다름을 확인한 후 시작한다.
- 삭제 기록 후보의 분석 한도는 작업당 100,000개다. 복사본·휴지통·카빙 및 일부 부가 기능의 기존 10,000개 한도는 유지한다. 한도 도달 시 미완료·잘림·검사 범위가 남았음을 표시한다. 화면 페이지 제한과 엔진 분석 한도는 별개다.
- 최근 저널 읽기는 전체 시간순을 증명하지 못한다. 읽지 않은 이전 구간에 시각 미상·시계 변경 사건이 있을 수 있으므로 부분 검색으로 보고한다. ‘보존된 삭제 이력 전체 확인’도 현재 남아 있는 저널의 범위이며 이미 사라진 과거 이력은 보장하지 않는다.
- `bytesRead`는 API가 실제 반환한 바이트 수다. USN 주소 구간의 차이를 절감한 실제 읽기 바이트 수로 바꾸어 말하지 않는다.
- 문서 미리보기 성공은 전체 문서의 정상 열림이나 삭제 전 원본과의 동일성을 증명하지 않는다. 현재 문서 앱의 전체 열림을 자동으로 검증했다고 표시하지 않는다.
- 파일을 기록한 뒤 재읽기 확인에 실패하면 ‘저장 파일 중 확인 실패’로 따로 집계한다. 실제 출력 기록을 미저장으로 세거나 정상 문서로 세지 않는다.
- 일반 삭제 기록에도 서로 다른 실제 이름이 여러 개 있으면 `recovered-record-번호.확장자`라는 임시 이름으로 저장하고 이름 후보를 남긴다. 모호한 부모 경로를 원래 경로로 복원하지 않는다. 같은 부모의 긴 이름과 DOS 별칭은 이 경우와 구별한다.
- 준비 단계에서 확인한 미지원 구조·상태 충돌은 실패 보고서에 후보 상태와 설명을 유지한다. 모르는 실패 원인으로 바꾸지 않는다.
- 기록 진단에는 본문 원시 바이트를 넣지 않는다. 원시 기록 전체 해시와 제한된 구조·영역별 비교 근거를 남긴다. 0으로 읽히거나 기록이 재사용됐다고 해서 본문의 물리적 소실을 확정하지 않는다.

## 이번 시험의 범위

엔진 회귀 시험은 284개 중 283개 통과, 실패 0개다. Windows의 심볼릭 링크 생성 권한 부족으로 1개는 건너뛰었다. 개발 실행과 배포 실행 파일의 Electron 화면·IPC 시험은 각각 5/5 통과했다.

합성 NTFS 이미지에서의 실제 작업자 복구와 이전 실제 시험 결과의 재평가를 포함한다. 대량 후보 시험의 일부는 정답 후보를 보관 순서 10,000번째 뒤로 옮기는 합성 시나리오다. 실제 SSD에서 새 파일을 생성·삭제·복구한 성공률 시험과 구별한다.

이번 변경을 기존 실제 C: 혼합 문서 시험의 0/6 실패가 6/6 성공으로 바뀌었다는 근거로 쓰지 않는다. SSD 원본 복구율과 독립 도구 비교는 이후 체크리스트에서 별도로 측정한다.

최종 시험 로그·변경 전후 자료·독립 검토는 1단계 증거 폴더 (개발 당시 로컬 증거; 공개 요약은 docs/EVIDENCE.md)에 보관한다. 최종 인수 결과는 같은 폴더의 `acceptance.md`에 기록한다.
