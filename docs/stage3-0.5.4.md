# 0.5.4 — 정답을 분리한 반복 시험과 PDF 경계 수정

정밀 검색에서 선형화 PDF를 첫 내부 `%%EOF`까지만 저장하던 문제를 수정했다. 첫 객체의 선형화 사전을 제한된 범위에서 해석하고, 전체 길이·마지막 종료 표시·기본 교차 참조 위치를 확인한다. 선언된 길이 밖 읽기, 잘못된 사전, 중복 키, 손상된 꼬리, 인식 가능한 추가 저장 이력은 정상 추출로 처리하지 않는다. 일반 PDF의 기존 경로는 유지한다.

이 검사는 파일 범위의 구조 검사다. 모든 객체·스트림의 무결성, 복호화, 원래 이름, 삭제 전 원본 동일성을 보증하지 않는다. 선형화 교차 참조 스트림과 일반적인 증분 저장 재조립은 미지원이며, 바로 뒤의 4 KiB에서 인식되는 추가 저장은 보수적으로 거절한다. 머리말 사전 검사도 4 KiB·토큰·깊이 한도가 있다. 카빙 파일명은 계속 생성한 이름으로 표시한다.

## 시험 구분

- 자체 문서 18개: 개발/별도 평가 각각 TXT·PDF·DOCX × 작은 파일·약 16 KiB·약 1 MiB. 한글·긴 이름·동명·다른 폴더를 포함한다. PDF는 빈 페이지와 검증용 콘텐츠 스트림이므로 실제 업무 문서의 시각적 복잡도를 대표하지 않는다. 1 MiB를 넘는 대형 업무 문서·GB급 파일은 이 시험의 범위 밖이다.
- 각 군을 연속 배치·조각 배치·MFT 기록 재사용·머리말 덮어쓰기·본문 0 채움으로 구성한 고정 이미지 10개. 각 이미지 9개 대상, 메타데이터/정밀 검색을 각각 2회 실행한다. 같은 생성기를 사용한 평가군은 독립 매체 표본이 아니다.
- 압축·희소·확장 속성 목록의 정상/손상 이미지 6개를 추가한다. 엔진에는 이미지 전체만 주고, 정상 3개는 정확한 바이트를, 손상 3개는 해당 본문 저장 거절을 요구한다.
- NIST NTFS 삭제 파일 이미지 2개에서 문서화된 Bunda.txt 구간을 비교한다. 정답 해시는 공식 이미지의 문서화된 위치에서 독립 산출했으며, NIST가 별도로 게시한 원본 해시라고 주장하지 않는다.
- NIST L0 문서 카빙 이미지의 원본 7개는 NIST 원본 파일을 별도 내려받아 비교한다. 이 자료에서 PDF 오류를 발견해 수정했으므로 **수정 후에는 개발 회귀 자료**다. 별도 평가로 남겨 둔 자체 군과 구분한다.

복구 프로세스 인자는 엔진 경로·이미지 경로·검색 방식·출력 폴더뿐이다. 원본 이름·해시·기록 번호·본문 위치는 전달하지 않는다. 부모는 검색과 출력 해시 고정을 마친 뒤 정답을 읽는다. 이는 코드/프로세스 입력 분리이며 동일 계정의 파일 접근을 차단하는 OS 샌드박스는 아니다.

## 인수 증거

| 고정 시험 | 0.5.3 | 0.5.4 | 해석 |
|---|---:|---:|---|
| NIST L0 원본 7개, 2회 | 원본 일치 10/14 | 14/14 | 매회 PDF 2개가 추가로 정확하게 저장됨 |
| 별도 자체 평가군, 2회·두 검색 방식 | 양성 64/64 | 64/64 | 이번 수정으로 관측된 퇴행 없음 |
| 자체 개발군, 2회·두 검색 방식 | 수정 전 64/64 | 양성 64/64 | 180개 대상 판정 중 양성 분모 64 |
| 압축·희소·확장 기록 정상/손상, 2회 | 이번 비교 미실행 | 양성 6/6, 손상 거절 6/6 | 12개 판정 모두 기대와 일치 |
| NIST NTFS 원본 2개, 2회 | 이번 비교 미실행 | 4/4 | 공식 배치 문서에서 독립 산출한 정답과 일치 |

별도 자체 평가군은 연속/조각 배치의 메타데이터 복구가 각각 9/9이고, 기록이 재사용된 군은 메타데이터 0/9·정밀 검색 6/9다. TXT와 기록 내부에만 있던 본문에는 같은 카빙 경로를 적용할 수 없다. 자체 군은 각각 총 180개 판정이고, 64개 양성 외에는 원본 일치로 잘못 인정하지 않는지와 기록 부재 조건을 채점한다. 모든 음성 사례에 저장 거절을 요구하는 시험은 아니다. 실제 삭제 성공률의 분모로 사용하지 않는다.

덮어쓰기·본문 0 채움의 메타데이터 경로는 각 군에서 원본과 다른 본문 36개씩을 저장했다. 보충 감사 `changed-body-state-audit.json`은 두 군의 72개 출력 해시와 실제 문서 판정을 다시 검사했다. TXT 24개는 `needs-check`, PDF/DOCX 48개는 `format-mismatch`였고, 모두 원본 동일성·앱 열림 확인이 false이며 원본 복구 성적은 0개다. 이 보충 감사를 통해 손상/불명 표시를 확인했다. 기본 채점기의 실패 0개만으로 이런 표시나 저장 거절까지 입증됐다고 해석하지 않는다. `metadataRefused`로 저장 자체를 거절해야 하는 별도 고급 구조 손상 사례 6건과 구분한다.

증거 루트: `E:\RecoveryChat-NextStage-20260920`. 각 실행의 configuration/summary, 고정 result.json과 해시, 입력 전후 해시, 출력 해시·크기, 엔진·시험 도구 해시, 실행 시간과 오류를 보관한다. 원본 일치의 분모는 알려진 대상이며, 이름만 남은 기록이나 배경 후보를 복구 성공으로 합산하지 않는다. 손상 원본을 추출했더라도 원본 일치로 계산하지 않는다.

실제 삭제 절차 F14는 `E:\RecoveryChat-Capture-20260920\live`의 0.5.3 시험 10회·50건을 사용한다. 생성 후 파일 동기화·닫기·읽기 해시 비교, 원본과 휴지통 $I/$R의 연결, 개별 제거 영수증을 보관했다. 이번에는 기존 증거를 새 보고서 `prior-live-audit-refreshed.json`으로 다시 감사했고 오류·경고 0개다. 파일 동기화는 OS가 보고한 완료이며 NAND 물리 상태 정지를 증명하지 않는다. 이번 0.5.4 작업에서 실제 C: 삭제 시험을 새로 실행한 것은 아니다.

F13은 원본·정답 해시·이름·경로·크기와 생성 시각/합성 메타데이터의 고정 시각·이미지 해시 및 실제 삭제 영수증 분리를, F15는 위 문서 크기 범위를, F16은 정상/손상 고정 입력과 기대 판정을 인수 범위로 한다. F17은 공식 자료와 엔진 수정에 사용하지 않은 자체 평가군을, F18은 전후 버전·반복·실패를 포함한 기록을 근거로 한다. 2단계 F07의 실제 USB 브리지·4Kn·잠긴 BitLocker 인수는 여전히 남아 있다.

## 재실행

새 출력 폴더를 지정해야 하며 기존 증거를 덮어쓰지 않는다. 복구 프로세스가 끝나기 전 정답을 읽지 않는다. 빈 시험군·잘못된 정답·변경된 입력·실행 오류는 통과로 집계하지 않는다.

```text
python scripts/qualification-documents.py <new-documents-directory>
node scripts/qualification-fixtures.mjs <documents/manifest.json> <new-corpus-directory>
node scripts/qualification-advanced.mjs <new-advanced-directory>
python scripts/qualification-public-carving.py <new-public-directory>
node scripts/verify-stage3.mjs <plan.json> <oracle/answers.json> <engine-root> <new-output-directory> development 2
node scripts/verify-stage3.mjs <plan.json> <oracle/answers.json> <engine-root> <new-output-directory> evaluation 2
```

문서 생성에는 pypdf·python-docx가 필요하다. 생성기·채점기는 개발 도구이고 최종 앱의 시작 시 실행되거나 백그라운드에서 삭제 작업을 하지 않는다.
