# 0.5.13 — 빈 기록 검색에서도 최근 본문부터 확보

0.5.12의 실제 C: 시험은 삭제 기록 50/50개, 원본 내용 일치 24/50개였다. 기본 검색은 최신 삭제부터 처리했지만, 그 다음 빈 기록 검색은 MFT 번호 순으로 확인했다. 모든 빈 기록 검색에서 즉시 확보 시도 64회 한도가 소진됐고 추가 원본 동일 복구는 0개였다. 구체적인 소비 대상이 모두 오래된 파일이었다고 확정한 것은 아니다. 코드의 처리 순서에서 최신 파일이 한도 뒤로 밀릴 수 있는 경로를 확인했다.

## 변경 범위

빈 기록 검색에서 본문 확보가 켜져 있고 Windows 삭제 이력이 있으면, 관측된 삭제 시각이 최신인 후보를 먼저 확인한다. 최대 64개 기록, 기록 사이에서 확인하는 2초 시간 예산으로 제한한다. 진행 중인 한 파일의 안전 확인·읽기를 2초에 강제 중단하는 상한은 아니다. 기존 본문 확보의 별도 크기·시간·시도 한도는 유지한다.

- 이름·부모·정확한 다음 세대, 미사용 MFT 비트와 현재 데이터 할당을 기존 방식으로 확인한다. 삭제 이력만으로 본문 읽기를 허용하지 않는다.
- 이 우선 처리가 끝나거나 한도에 닿아도 전체 빈 기록 비트맵 탐색은 이어진다. 같은 기록의 동일 지문은 후보와 본문 확보를 중복하지 않는다.
- 삭제 시간이 없는 후보는 최신이라고 추정하지 않고 뒤의 빈 기록 탐색에서 확인한다. 선택 기간 밖의 확인된 삭제 이력도 최신 우선 대상으로 사용하지 않는다.
- 이력이 없거나 본문 확보가 꺼져 있으면 기존 빈 기록 경로로 진행한다. 저널 전체 수집, 잘못된 시작점의 기존 재시도, 기본 검색 경로와 기존 후보·취소 한도는 유지한다.
- 새 버튼은 없다. 진행 안내에 ‘최근 삭제된 파일 본문 먼저 확보 중’을 표시하고, 이후 빈 기록 탐색으로 넘어간다. 내부 `recentPriority` 통계에 시도 수·본문 후보 수·경과 시간·종료 이유를 기록한다. 우선 처리 완료를 전체 검색 완료로 세지 않는다.

## 같은 입력 비교

정상 TXT 본문이 남아 있는 합성 NTFS 이미지에 오래된 낮은 번호 파일 70개와 가장 최근의 높은 번호 파일 1개를 배치했다. 두 버전을 번갈아 각각 3회 실행했다. 검색 엔진에는 파일 정답·해시·알려진 대상 번호를 주지 않고 동일 이미지와 합성 저널만 주었다. 후보를 먼저 고정한 뒤 별도 정답과 SHA-256을 대조했다.

| 항목 | 0.5.12 | 0.5.13 |
|---|---:|---:|
| 최신 파일 처리 순서 | 71번째 | 첫 번째 |
| 최신 파일 원본 일치 확보 | 0/3회 | 3/3회 |
| 회당 전체 후보 | 71개 | 71개 |
| 회당 원본 일치 확보 | 64개 | 64개 |

전체 확보 개수는 같다. 최신 파일이 오래된 파일 하나보다 먼저 한도를 사용하는 변경이다. 총 복구율 향상이나 실제 SSD의 48%가 올라갔다는 증거가 아니다. 고정 이미지에 남아 있는 본문과 살아 있는 시스템 SSD의 상태 변화를 구분한다. 캐시를 비우지 않은 순차 측정이며 전체 검색 속도 향상을 주장하지 않는다.

재현 명령:

```powershell
node scripts/verify-recent-priority.mjs <0.5.12-engine-folder> <current-engine-folder> <fresh-output-folder>
```

증거: `E:/RecoveryChat-RecentPriority-0513-20260926/`. 새 우선 처리 시험 11개와 전체 엔진 시험은 **535 통과·실패 0·기존 환경 제한 1개 제외**다. 개발 화면 진행 상태 시험 1개도 통과했다. 패키지 화면·소스 대조와 최종 독립 검토 결과는 해당 폴더의 `acceptance.json`에 보존한다.

## 남은 범위

F20/F24 일부 보강이며 필수 인수 **17/54(31.5%) 유지**다. 새 실삭제 시험은 이번 보강에서 수행하지 않았다. 가장 최근 실제 결과는 별도 `E:/RecoveryChat-Performance-0512-20260926-172339/성능테스트-결과.md`의 0.5.12 24/50개다. 기본 검색 시작부터 첫 본문까지의 초기화 지연, 기록 재사용 뒤의 본문 재발견, 정밀 검색과 원래 삭제 이력의 안전한 연결은 남아 있다.
