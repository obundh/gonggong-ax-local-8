## 새로 사용할 수 있는 기능

`도구 · 안내 → 최근 문서 이름·경로 단서 → 이름·경로 단서 찾기`를 일반 모드와 채팅 모드에서 사용할 수 있다. 기본 Windows Recent 폴더의 바로가기만 읽으며 다른 하위 폴더를 순회하지 않는다. 기본 한도는 후보 2,000개·바로가기 파일 10,000개·10초·바로가기 1MiB다. 중단·지원하지 않는 형식·읽기 실패는 별도 경고로 표시한다.

바로가기에 남은 이름과 경로, 바로가기 수정 시각, 경로 근거를 보여준다. 한글 ANSI 경로를 확정할 수 없고 Unicode 상대 경로가 있으면 문자열로 경로를 계산하여 **상대 경로에서 계산 · 실제 위치 미확인**으로 표시한다. 바로가기 수정 시각은 삭제·열람 시각이 아니다. 대상 파일을 열거나 존재 여부를 검사하지 않고 네트워크 경로도 따라가지 않는다. 본문·삭제 여부·원래 문서와의 동일성은 미확인이다.

단서만 있는 후보는 선택·복구·저장이 불가능하다. 원래 이름을 살린 복구 파일로 집계하지 않으며 미리보기 창은 본문 없음과 출처만 보여준다. 실제 Windows가 만든 한글 바로가기의 대상을 이동한 뒤에도 단서를 얻고, 저장을 거절하며, 대상 파일이 변하지 않는지 시험했다. 이 시험은 바로가기 메타데이터 기능 검증이고 삭제 파일 본문 복구 시험이 아니다.

독립 검토에서 실행 작업 폴더를 상대 경로 기준으로 쓰던 오류를 찾아 수정했다. 상대 경로는 바로가기 파일의 폴더를 기준으로만 계산하며, 실행 작업 폴더는 대상 위치로 사용하지 않는다. 이름이 반복되는 하위 폴더도 생략하지 않는다. [Microsoft StringData 명세](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-shllink/17b69472-0f34-4bcf-b290-eccdb8de224b).

기존 Office 자동 저장 검색의 제한 경고도 바로잡았다. 시간·폴더 순회 한도에 도달했을 때 후보 10만 개 상한이라는 관계없는 경고를 덧붙이지 않는다.

## 실제로 측정한 결과

- 독립 비교: 같은 고정 FAT16 입력에서 RecoveryChat와 TSK 4.15.0의 메타데이터 복구가 각각 원본 바이트 4/4, RecoveryChat와 PhotoRec 7.2의 자유 공간 PDF 카빙이 각각 3/3이다. 카빙 3개는 고유 본문 2개와 의도적인 동일 사본 1개이며, 오탐은 0이었다. 삭제 FAT 짧은 이름의 첫 글자는 살리지 못해 이름 정확 일치는 0/4다. 부모 재실행도 같은 결과였다. [설정·원시 증거·제한](independent-comparison-0.6.0.md).
- 자원: 부모 재실행에서 100,000개 수용·추가 10,000개 명시적 한도 거절, 가져오기 6.26초, 첫 20개 209ms, 마지막 20개 463ms, 배치 종료 시 표본 RSS 최대 113.13MiB, 저장소 약 62.97MiB였다. 호스트는 RAM 31.89GiB이고 OS 최고 메모리는 측정하지 않았다. 가져오기의 동기 작업은 작업자 안에 있어야 하며 8GB PC 인수로 세지 않는다. [예산·장치·연구 제약](resource-research-0.6.0.md).
- 기존 백업 확인: `Win32_ShadowCopy` 읽기 전용 조회가 “초기화 실패입니다.”로 실패했다. 스냅샷이 없다고 판정하지 않았으며 새 스냅샷을 만들거나 서비스를 시작하지 않았다. File History 기본 구성 폴더 미발견 역시 모든 외부 백업이 없다는 뜻이 아니다.

이번 작업은 새 실제 SSD 삭제 반복 시험을 하지 않았다. 이전 실패 35건과 비교하여 실제 SSD 복구율이 올랐다고 말할 근거가 없다. 기존 기록 재사용 관측과 정답 불일치 35건은 해결되지 않았고 TRIM·물리적 덮어쓰기 등 단일 원인으로 확정하지 않는다.

## 검증과 배포 인수 범위

최종 영수증: `E:/RecoveryChat-TenStage-0600-20260927/acceptance.json`과 같은 폴더의 `한국어결과.md`. 소스 변경 목록·검사 로그·독립 검토·패키지 일치 여부를 이 증거 묶음에 연결한다. 이 문서의 인수 수치는 해당 영수증이 통과한 최종 소스·배포본에만 적용한다.

검증은 엔진 시험과 실제 Electron 창 시험을 구분한다. Electron 시험은 일반/채팅 Recent 단서, 일반/채팅 Office 사본 목록·선택·미리보기·저장, 손상 DOCX의 부분 텍스트 저장을 실제 IPC·작업자로 실행한다. 원본 폴더 위치와 네이티브 파일 선택 응답은 소유 고정 자료로 주입하며 Windows 파일 선택창 조작·실제 Office가 생성한 복구본·실제 SSD 삭제 시험을 대신하지 않는다. 복사 출력과 입력의 SHA-256, 부분 추출 출력 해시, 원본 불변, 사용자 문구를 함께 검사한다. 단서에는 저장 버튼이 없는지 확인한다.

패키지는 `E:/RecoveryChat-0.6.0/RecoveryChat-0.6.0-win-x64.zip`과 `win-unpacked/`다. Electron 44.3.0과 기존 읽기 도우미를 사용하며 새로운 런타임 의존성을 추가하지 않는다. 소스 대 패키지, ZIP 대 풀린 파일의 해시를 검사하고 개발용 비교 도구·시험 데이터가 제품에 들어가지 않는지 확인한다. ZIP 전체를 풀어 EXE를 실행해야 한다. 다른 PC는 원본과 별도 물리 디스크에서 실행한다.

TSK와 PhotoRec은 별도 E: 시험 폴더에서만 사용했고 제품에 동봉하지 않았다. [고지](../THIRD_PARTY_NOTICES.md). 0.6.0은 코드 서명·전체 장비 호환·포렌식 인증을 새로 획득한 배포가 아니다.

## 보류를 재개할 때

쉽게 추가할 수 있는 다음 증거는 개발에 쓰지 않은 NTFS·DOCX 비교 입력과 8GB PC의 자원 계측이다. 4단계의 재사용 기록과 일반 문서 조각 재조합은 별도 정답 자료가 있어야 한다. SSD 내부 복구는 모델별 진단 접근·매핑·ECC·암호화 상태와 연구용 매체 없이 앱 코드만 추가해 해결됐다고 할 수 없다. 각각의 구체적인 시작 조건은 체크리스트에 적었다.
